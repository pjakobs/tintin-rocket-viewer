1. Overview

The app is a single-page, client-only 3D viewer. It loads an LDraw .ldr model (a plain-text brick-by-brick assembly description) with Three.js's built-in LDrawLoader, keeps every LEGO part as its own addressable Object3D, and layers interactive features — explode, build-step scrubbing, click-to-inspect, per-brick hide, and shareable deep links — directly on top of that per-part hierarchy.

There is no backend, no build-time model processing beyond static asset copying, and no framework: six small ES modules coordinate through a single shared model object and the DOM.

window.viewer = { THREE, scene, camera, renderer, controls, model }   (console/debug escape hatch —
                                                                        model is data only; see §12)

Coordination is deliberately flat, but no longer mutates a shared object to get there: main.js constructs the scene and the plain-data model, then calls initFeatures(model), initHotspots({ …, features }), and initStateSync({ …, features, hotspots }) in turn, each returning an API object rather than attaching methods onto its input. The call signatures themselves make the dependency order explicit — hotspots needs features, state needs both — instead of an unenforced convention that only breaks when a deep-linked URL happens to exercise a restore path. Cross-module notification is a single onChange slot per returned object (features.onChange, hotspots.onChange), both wired by main.js to state.scheduleWrite — one path per module, not two independent ones for what is logically the same change.

4. Module reference

src/main.js — 287 lines

Entry point. Owns the Three.js scene, renderer, camera, lighting, and the LDrawLoader setup. Fetches and parses the model, counts placed meshes, frames the camera on load, and runs the render loop. Also implements Recentre (undoing pan drift in the orbit target) and the missing-parts tally (a LoadingManager.onError/onProgress hook, replacing an earlier console.warn-text-matching interceptor). Constructs features / hotspots / state and wires their onChange slots together; model itself is just { root, bricks, maxStep, fingerprint }.

onModelLoaded(group, text)post-load fixups (edge materials, upright rotation), then constructs and wires the three feature modules
frameModel(object)centres the model on its axis of symmetry and fits the camera to its bounding sphere, leaving headroom for a 300% explode
recentre()moves camera + orbit target back by the same delta to undo a pan, without touching zoom/angle

src/features.js — 252 lines

Everything driven by the Explode and Build step sliders, plus per-brick hide/restore. Collects the ~1,181 "brick groups" (outermost Object3Ds whose userData.fileName is a .dat part), stamps each with its own index, and pre-computes a local-frame displacement vector per brick so the exploded-view update is a single copy + addScaledVector per frame. initFeatures(model) returns an API object rather than mutating model with methods; view = { explode, step } is the one source of truth sliders read from and write to via setView(patch) — no more synthetic dispatchEvent to reconcile Play-build's programmatic slider updates with the drag-driven ones.

setView({ explode, step })merges into view, re-renders sliders/labels/3D, and calls onChange — explode is 0–3, scaling every brick's precomputed displacement
applyVisibility()the single writer of group.visible — ANDs the step test with the hidden flag
setHidden / unhideLast / showAllHiddenper-brick hide, backed by a most-recent-last stack for U / Cmd+Z
Play buildrequestAnimationFrame loop calling setView({ step }) over ~22s
dispose()removes the DOM/window listeners this module added; not wired to anything yet

src/hotspots.js — 232 lines

Click-to-inspect. Raycasts against a flat list of brick meshes, resolves a hit back to its brick group via a mesh → brick map built from features.bricks, and shows an emissive-material highlight plus an oriented Box3Helper computed in the brick's own local frame (so it hugs rotated parts and follows them through an explode). Distinguishes a click from an orbit-drag by pointer-travel distance. Lazily fetches each part's human-readable description from its .dat file's header comment. Takes { camera, renderer, features, libraryPath } — no more unused THREE / scene params, and no controls passed in at all (it never used it).

selectBrick(brick) / deselect()public entry points, also used by state.js to restore a deep-linked selection; own selectedIndex and call onChange directly via brick.index, no indexOf scan
pick(x, y)raycast helper; skips bricks hidden by the step scrubber
hideSelected()deselects first (restoring materials) then calls features.setHidden
dispose()removes the pointer listeners and clears the current highlight (keymap bindings aren't unregistered — see keymap.js)

src/state.js — 154 lines

Deep-links explode amount, build step, selected/hidden bricks, and camera position+target into location.hash as a short key=value string, reading features.view, features.hiddenIndices, and hotspots.selectedIndex directly rather than DOM element values. Only keys that differ from the default view are written. Writes are debounced with a max-wait (350ms / 600ms) because OrbitControls damping keeps firing change events long after a drag ends. Construction only wires the camera listener and the share button; restore() is a separate call the caller makes explicitly once features.onChange / hotspots.onChange are wired, replaying the hash in a fixed order — hidden bricks before selection, so a brick that's both hidden and selected stays hidden. The restoring flag suppresses scheduleWrite during that replay.

src/keymap.js — 33 lines

One window.addEventListener('keydown', …) for the whole app, replacing three independent registrations (in main.js, features.js, hotspots.js) that each re-implemented the "don't steal slider keys" guard and hand-rolled modifier checks in three different shapes. bindKey(combo, fn, { label }) throws on a duplicate combo instead of silently letting a later binding shadow an earlier one. keyHints() returns { combo: label } for every labelled binding, so the two on-screen hint strings (HUD, inspect panel) are rendered from the same source of truth as the bindings themselves rather than hand-kept in sync with them.

src/geometry.js — 30 lines

One pure helper, axisOfSymmetry(), shared by main.js (camera framing) and features.js (explode direction) to avoid an import cycle. Computes the model's true vertical axis as the mean of every brick's own centre, rather than the bounding-box centre — the splayed landing legs pull a bbox centre ~53 LDU off-axis.

src/crosscheck.js — 106 lines

Runtime sanity check, independent of rendering: expands the raw LDraw MPD text to per-part leaf counts and reconciles them against the manual-derived rebrickable_parts.csv. Runs off the same model text the viewer just loaded, so what's counted matches what's rendered. Results populate the HUD's "Manual CSV" row and a detailed breakdown in the console (console.groupCollapsed).

5. Load lifecycle

  1. index.html loads src/main.js as a module.
  2. Scene, renderer, camera, lights, and OrbitControls are constructed synchronously.
  3. loader.preloadMaterials(LDConfig.ldr) — awaited so real LEGO colours are known before parsing.
  4. fetch() the .ldr model text, then loader.parse(text, …) (not loader.load() — see §10).
  5. onModelLoaded() rotates the model upright, patches null edge-line materials, counts meshes, adds the group to the scene, then calls frameModel() and updateHUD().
  6. const features = initFeatures(model) → const hotspots = initHotspots({ …, features }) → const state = initStateSync({ …, features, hotspots }), in that order — each call signature requires the previous object, so the ordering is enforced by what the functions accept rather than by convention.
  7. features.onChange = state.scheduleWrite; hotspots.onChange = state.scheduleWrite; then state.restore() — wiring happens before restoring, so a restored selection or hidden brick would notify scheduleWrite like any other change; the restoring flag inside state.js is what actually suppresses the write during replay.
  8. crossCheck(modelText) runs asynchronously and patches the HUD when it resolves.
  9. animate() starts the render loop (already running from module load; rendering an empty scene until step 5 populates it).

6. The brick data model

The central data structure is model.bricks, an array built once in initFeatures() and also returned as features.bricks (same array, same objects — model is the data bag, features is the behaviour that reads and writes it): 

model.bricks = [
  {
    group,   // THREE.Group — the brick's own Object3D (userData.fileName, .buildingStep, .colorCode)
    step,    // LDraw build step this brick appears at
    home,    // group.position at load time (assembled position)
    dir,     // precomputed local-frame displacement vector at 100% explode
    hidden,  // per-brick hide flag
    index,   // this entry's own position in the array
  },
  ...
]

This is the shared vocabulary every feature module operates on: features.js writes group.position / group.visible from it, hotspots.js builds a mesh → brick lookup from it for raycasting and reads brick.index to set selectedIndex, and state.js references entries by that same index for URL links (p= for selection, h= for hidden). Both reads used to be an entries.indexOf(brick) scan over ~1,181 entries per lookup; the stamped index makes it O(1).

Positional indices are why a model-file change (like splitting out the minifig gear) can silently resolve a link to the wrong brick — this already happened once. model.fingerprint (also set by initFeatures(), an order-sensitive hash over the brick list) guards against it: see §7.

7. URL state / deep linking

Format: a short &-joined key=value hash string.

#e=35&s=200&p=300&h=41,88&v=1ysb0ap&cx=527&cy=154&cz=2604&tx=0&ty=0&tz=0
KeyMeaning
eexplode amount (0–300)
sbuild step
pselected brick — index into model.bricks
hcomma-separated hidden brick indices
vmodel.fingerprint at write time — only present when p= or h= is; see below
cx/cy/cz, tx/ty/tzcamera position and orbit target

Only keys that differ from the default view are written, so a plain visit keeps a clean URL. The Copy link button flushes the debounced write immediately before copying.

p=/h= are positional indices into model.bricks (§6) — meaningless if the brick list has changed shape since the link was made. Rather than resolving an in-range index to a different brick, restore gates both keys on an exact v= match against the current model.fingerprint; a missing v= counts as a mismatch (it predates this check). On mismatch, p=/h= are dropped and a dismissible notice explains why — camera, explode and step still restore, so a stale link degrades rather than failing wholesale.

8. Offline build pipeline (scripts/)

These are one-off/occasional Node scripts, not part of the app's runtime — they regenerate committed assets under public/.

strip-loose-elements.mjs
Splits the untouched master Studio export into the rocket-only model the viewer renders (public/model/tintin-rocket.ldr) and the 74 loose minifig-gear bricks (references/minifig-gear.ldr), which sit ~500 LDU off to the side and would otherwise inflate the model bounds and skew the explode centroid.
extract-custom-parts.mjs
Pulls the two BrickLink Studio-proprietary parts (bl_8097 nose cone, bl_98138pb459 printed tile) out of the Studio .io export's embedded geometry, normalising prefix/version differences across Studio releases, and writes them as real .dat files into the library.
prune-library.mjs
Walks the ~820MB full LDraw library from a root-level ldraw-library/ (kept out of public/) and copies only the ~529 parts/primitives this model + the split-out minifig gear reference into public/ldraw-min/ (~2.7MB), which is committed and served.

Regeneration order, per the README:

node scripts/extract-custom-parts.mjs     # 1. add Studio custom parts to ldraw-library/
node scripts/prune-library.mjs --apply    # 2. slim to public/ldraw-min/

10. Notable design decisions & gotchas

LDrawLoader over a Blender → glTF bake

A Blender import/export would bake everything into a handful of material-batched meshes — faster to render, but it destroys per-part identity. LDrawLoader keeps every brick as its own Object3D carrying its LDraw part number and build step in userData, which every interactive feature (hotspots, explode, build scrubbing) depends on. Verified coverage: 129/133 unique parts from the official library, 131/133 with the unofficial add-on, and the remaining 2 Studio-proprietary parts extracted from the .io export — 0 missing at runtime. Performance: 1,181 bricks → 1,228 meshes, ~674k triangles, ~3,630 draw calls, 60fps on a normal desktop GPU with no merging.

Four r0.171 gotchas fixed in main.js:
  1. loader.setConditionalLineMaterial(...) is mandatory or parsing throws.
  2. loader.load() calls setMaterials([]) internally and discards preloaded colours (renders everything magenta). Use preloadMaterials() + fetch() + loader.parse() instead.
  3. Edge LineSegments can come back with a null material and crash the renderer at material.visible — patched with a shared LineBasicMaterial post-load.
  4. Vite's SPA fallback serves index.html for a missing .dat, which the loader then tries to parse. Fixed with appType: 'mpa' so missing parts are real 404s.

Axis of symmetry, not bounding-box centre

The three landing legs splay asymmetrically; a bounding-box centre is dragged ~53 LDU off the rocket's real vertical axis by the leg tips. geometry.js's axisOfSymmetry() instead averages every brick's own centre — dominated by the symmetric body, landing within ~1.3 LDU of the true axis. Used both for camera framing (avoids visible orbit swing) and for explode direction (avoids fanning one side of a ring further than the other).

Visibility has exactly one writer

Two independent things can suppress a brick — the build-step scrubber and per-brick hide. features.js's applyVisibility() is the only code path that assigns group.visible, computing it as step <= currentStep && !hidden. Setting visible anywhere else would work until the next scrubber tick or Play-build frame silently resurrects the brick.

Recentre vs. the axis fix — two different bugs

The axis-of-symmetry fix corrects a fresh-load framing bug. Right-drag panning in OrbitControls slides the camera and orbit target together, so after a pan the camera pivots about wherever the target landed — off-axis, and persisted into the URL hash, so it survives a reload. recentre() in main.js is the separate fix for that: it moves both camera and target back by the same delta, leaving zoom and orbit angle untouched.

BrickLink/LDraw part-number collisions

BrickLink's part numbering can collide with unrelated LDraw part numbers for the same digits (BrickLink 8097 is a different cone shape from LDraw's 8097.dat, with a different local origin). Aliasing the Studio custom part to the LDraw file of the same number renders the nose cones splayed outward like ears. extract-custom-parts.mjs instead pulls Studio's own embedded geometry so the model's transforms place it correctly.

11. Build & deployment

npm run devVite dev server
npm run buildstatic production build to dist/
npm testvitest run — pins crosscheck.js, state.js, and geometry.js's pure helpers (§4)
npm run deployvercel build --prod && vercel deploy --prebuilt --prod

Deploys from prebuilt output rather than letting Vercel build from source, because a plain vercel --prod tries to upload the whole working directory and hits Vercel's 15,000-file cap (mostly node_modules). The GitHub repo is private and not auto-deploy-connected, so npm run deploy is the sole publish path.

12. Extension points

window.viewer exposes { THREE, scene, camera, renderer, controls, model } for console-driven exploration. As of the §3 composition refactor, model is data only (root, bricks, maxStep, fingerprint) — it no longer carries setExplode / setStep / setHidden / unhideLast / showAllHidden / selectBrick / deselect as callable methods. That behaviour lives on the features / hotspots / state objects main.js's onModelLoaded() builds locally (§3) — not reachable from window.viewer without adding a debug export there, a deliberate tradeoff (see the remediation plan's D2) against keeping the god-object pattern the refactor removes just to preserve a console one-liner.

  • Isolate / colour-by: model.bricks gives every brick its step and metadata already — tint by step for a build-order heatmap, or filter by group.userData.fileName / colorCode to isolate a part type or colour.
  • Inventory linking: join a selected part number against crosscheck.js's parsed CSV data to show set-level quantities/spares next to the in-build count.
